# 应用内 SRE Agent 增强方案（提案）

日期：2026-09-21。状态：P0 第一批已在本地实现（7 个诊断工具、两项内置技能、会话证据），尚未发布；后续阶段仍为设计建议。本轮仅写方案，不修改业务代码，不推送 GitHub、不发布版本；后续上传须用户明确指令。

## 1. 目标与现状

目标：让应用内 Agent 能完成服务器巡检、基于证据的故障定位、授权变更及验证交付；后续支持用户配置 Agent 和工作流。

现有实现：四档权限、SSH 服务器目标、命名会话、暂停/继续、审批及任务记录；7 个工具 list_files/read_file/write_file/make_directory/inspect_system/run_command/http_check。工具名称、Schema 和权限判断写死在 agent-contract.ts/shared agent.ts；只读模式禁止 run_command；http_check 限目标服务器回环 HTTP。模型上下文只保留最近 20 步并截断输出，有 200 步会话上限。

主要缺口：日志、指标、服务、网络没有独立结构化诊断工具；排障流程依赖临时推理；没有应用内 Skill 加载与插件生命周期；长任务缺少独立事实/计划记录与检查点。现有外部 HTTP Agent 是返回分析与脚本的接口，不等于插件执行宿主。

Codex 用户目录中的 Skill 只作用于开发助手，不自动成为本应用的能力。应用内须实现独立运行时与存储。

## 2. 分层架构

用户需求 → Agent 运行器 → Skill 选择/加载 → Tool 注册与授权 → SSH / 内置服务 / 外部适配器 → 证据与验证。

- Tool：具有参数、结果契约的具体操作，例如查询 systemd 状态。负责执行事实，不负责决定授权。
- Skill：可读的运维方法、适用条件、步骤、判断分支和验收规则；只能调用已注册且已授权的工具。
- Plugin：可安装、启停、升级和卸载的能力包，打包 Skill、工具适配定义及兼容信息；不自行提升权限。
- Agent 配置：角色、模型、允许的能力、目标范围、权限和预算的组合，不复制一套执行引擎。
- Workflow：带输入输出、分支、暂停点、重试条件和恢复检查点的步骤定义；不能把自由文本计划直接当已执行事实。

首版保留现有串行执行器、SSH 凭据存储和任务管理，逐步替换硬编码工具表，避免同时重写整个平台。

## 3. Tool 层：先强化诊断，再增加变更

以下均为建议接口名，不是当前已实现工具。

| 能力 | 建议工具 | 结果与用途 |
| --- | --- | --- |
| 环境与资源 | host.facts、host.resources、clock.status | OS/软件/负载/内存/磁盘/inode/时间偏差，注明观测时间 |
| 服务 | service.status、service.logs | systemd 状态、退出原因、限定时间及条数的日志 |
| 容器 | container.list、container.inspect、container.logs | 健康、重启次数、端口与挂载信息 |
| 网络 | network.listeners、network.resolve、network.probe | 监听端口、DNS、指定目标连通性；参数化，限制范围 |
| 监控 | metrics.query、metrics.range、monitor.targets、grafana.datasource_check | 复用平台已有方案与连接，获取采集状态和指标证据 |
| 配置 | config.read、config.validate、config.diff | 受控读取、语法校验、变更差异 |
| 变更 | config.apply、service.action、deployment.apply | 保存变更前状态、执行、返回操作标识与健康检查 |
| 恢复 | change.inspect、change.rollback | 核实操作状态；仅对明确支持回滚的变更提供恢复 |

注册项包含命名空间、版本、输入/输出 Schema、执行位置、风险类别、是否产生副作用、超时、输出限额、前置条件、所需能力、验证规则。保留旧 7 个名称作为兼容入口，使旧记录和模型接口继续可用。

只读工具使用应用维护的固定命令模板与严格参数校验，不接受任意 shell 字符串；例如 service.logs 接收 unit/since/limit。不能根据命令名字、正则或插件自报的 readonly 就把任意命令认定只读。文件和日志需脱敏且限制数据范围。

结果统一为状态、结构化数据、证据引用、时间、目标、退出码、截断信息；大日志分页或保存为本地附件，不反复塞入全部历史。新增远端 HTTP/指标查询限定用户配置的目标和认证引用，不直接放开任意 URL。

## 4. Skill 层：首批 6 个内置技能

| Skill | 流程重点 | 成功标准 |
| --- | --- | --- |
| Linux 环境巡检 | 系统、资源、软件、端口、时间同步 | 所有结论可追溯采样；未知项明确列出 |
| 服务不可用排障 | 服务状态→日志→监听→配置→依赖→健康请求 | 给出证据支持的原因，区分推测与已确认 |
| Docker/Compose 排障 | 容器退出、健康检查、端口冲突、挂载和资源 | 明确故障对象和影响，不误操作其他项目 |
| Prometheus/Grafana 无数据诊断 | 时钟→targets→原始指标→时间范围→数据源→面板查询 | 定位断点，排除“服务存活即正常”的误判 |
| Nginx/Python 应用部署 | 环境与端口预检→计划→生成项目→配置检查→启动→HTTP验证 | 有真实页面、服务状态、访问地址及维护说明 |
| 变更验证与恢复 | 记录原状态→应用→健康检查→失败分析→有条件回滚 | 结果可核实；不可逆或恢复失败必须明确报告 |

每个包包含 SKILL.md、manifest.json（本项目自定义扩展元数据）、references/、受控模板及验收样例。元数据写明 id、版本、适用系统、触发条件、必需工具与权限；与通用 SKILL.md 格式区分，兼容导入不等于支持原运行环境。

默认只给模型技能索引，匹配后加载对应步骤与必要参考。可手动指定技能；会话显示采用的技能、版本和当前阶段。运行期间固定版本，更新不改变已开始任务。

## 5. Plugin 层与外部能力

第一阶段只交付内置 linux-core、container-ops、observability 三类能力包；Web 部署技能组合使用这些工具。用户能查看、启停和检查依赖，不先做在线市场。

第二阶段支持导入目录/ZIP：校验路径穿越、解压大小、依赖版本、摘要与兼容性；显示来源、能力和变更。卸载移除扩展注册，不删除服务器应用/数据。导入脚本不自动执行。

工具适配分为三类：应用内置适配器；经过配置的 HTTP/MCP 远程适配器；未来隔离进程适配器。MCP 只是接入协议，不代替工作台权限策略。第三方可执行代码不得直接加载到拥有凭据和数据库访问权的 Electron 主进程。首版不开放任意本地插件脚本执行，也不提供绕过 SSH 目标限制的本机工具入口。

依据：MCP 官方说明工具 annotations 只是提示，不应信任未知服务自报权限。
https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/

## 6. 权限与自主执行

保留分析建议、只读诊断、确认执行、自主执行四档，避免改变已形成的使用习惯。

有效能力 = 用户会话授权 ∩ Agent 配置 ∩ 插件允许能力 ∩ 工具策略 ∩ 目标账号实际权限。

自主执行在已授权目标/能力范围内连续操作，不重复逐步确认；若更换主机、新增能力、触及禁止资源或缺少关键信息则暂停。支持在任务开始时明确数据库/数据卷/SSH与防火墙配置等保护范围。权限由后端核验，Skill、日志与模型输出均不能改写授权。

对任意 shell 要诚实表达边界：命令不是沙箱；若需要严格限制文件、网络或系统操作，应使用受限账号、sudo 规则、结构化工具及相应隔离，不靠命令黑名单承诺强隔离。

## 7. 执行质量与证据

新增独立的 plan、facts、artifacts、checkpoints、verificationResults 记录；摘要与原始步骤分开，原始记录保留证据引用。事实包含来源时间与有效期，执行变更前刷新重要前置条件。

流程：观察→计划→执行→核验→总结。成功判据来自工具结果和技能预定义检查；模型 finish 不能单独证明服务正常。基础巡检缺少权限时输出部分结果与未检查项。

对限流/短暂网络读取错误可有限重试；写操作超时先核实是否生效，禁止盲目重放。配置写入带前置版本/摘要检查，避免覆盖其他人修改；变更按目标资源加锁。暂停保留边界语义，重新启动后对未完成操作先核实。

回滚不是任意动作的逆操作：配置可恢复备份，部署可切回明确版本；数据库迁移和删除数据不能承诺自动恢复。保留输出脱敏、预算、次数与时间上限。

## 8. 界面与后续工作台

AI 页保留当前对话结构：会话配置增加“能力方案/技能选择”；对话内展示计划、正在使用的技能、证据、变更差异和验收结果。执行记录继续留在 AI 模块，避免任务中心重复。

设置新增“Agent 与能力”：先提供内置技能/插件的查看、启停、依赖检查和权限说明；后续再开放自建 Agent（角色、模型、技能、工具、目标与预算）。工作流先用可验证的步骤表单和 JSON 定义，等调度语义稳定后增加拖拽画布。

## 9. 实施顺序与验收

P0 专业诊断底座：工具注册表与兼容层、结构化只读诊断工具、技能加载器、Linux巡检与监控无数据两项 Skill、证据呈现。验收：只读模式定位真实环境问题，零变更；原有会话/权限/暂停继续回归通过。

P1 可靠执行：配置差异与备份、服务/部署变更工具、检查点、验证和有条件回滚，补齐其他四项 Skill。验收：隔离测试应用部署成功；注入配置错误/端口冲突能定位，恢复后健康；不影响旧业务。

P2 扩展管理：能力包导入、版本与依赖、启停/卸载、选定 HTTP/MCP 接入。验收：未授权工具不可调用、越界包拒绝、版本固定、禁用立即影响后续调用、凭据不进入模型上下文。

P3 自建 Agent 与工作流：角色模板、技能组合、分支/重试/检查点、可视化编排。验收：中断继续不重复变更，多任务同资源互斥，旧执行记录仍可读。

建议先实施 P0，而不是一次同时开发插件市场、复杂画布和多 Agent 调度。

测试分层：参数/权限/解析单元测试；SSH/外部工具契约与故障注入；Electron 交互；经用户命令安排的 Rocky 实机验收。样例至少覆盖健康巡检、时钟偏差、采集目标 down、缺指标、服务失败、端口冲突、配置错误、权限不足、连接中断和提示注入。

发布约束：仅本地开发与验证，用户明确要求上传后才推送或发布。每阶段实际完成动作追加根目录项目进程.md。
